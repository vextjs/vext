# vextjs v2.0.0 candidate

**Candidate snapshot**: 2026-08-29
**Type**: Unpublished major-version candidate

## Status

This file describes the source candidate currently identified as `2.0.0`. It
does not claim that an npm package, Git tag, GitHub Release, or stable channel
has been published. Final publication remains blocked until genuine 2.x
external-consumer evidence is available at
`release/v2-external-validation.json` and the release channel is explicitly
chosen.

## Highlights

- Framework-owned SEO metadata, canonical URLs, robots directives, sitemap
  entries, route-level overrides, and named deployment origins.
- Route-level `hydration: "none"` for server-rendered HTML that intentionally
  ships no Vext/React browser runtime, hydration payload, or route JS preload.
- A single raw MonSQLize surface at `app.db`, with exact registered model keys
  and explicit collision handling.
- Opt-in global rate limiting: it is installed only when
  `rateLimit.enabled === true`.
- Executable Hello World and MongoDB CRUD examples covering build, runtime,
  validation, and OpenAPI behavior.
- Explicit TypeScript starter ownership under `src/types/shared`,
  `src/types/frontend`, and Vext-managed `src/types/generated`.
- An AI-first full-stack Node.js positioning grounded in conventions,
  scaffolding, typed contracts, OpenAPI, and machine-readable documentation;
  VextJS does not claim a built-in LLM, Agent, RAG system, or inference runtime.

## Release-candidate hardening

- Build and deploy filesystem boundaries fail closed before cleanup, serving,
  staging, or upload. Traversal, absolute paths, escaping symbolic links,
  duplicate manifest/upload keys, and content size or sha256 drift are rejected.
- Route scanning and runtime registration share canonical path identity and the
  same finite grammar. Doctor route manifests include source fingerprints and
  are rebuilt when stale unless `--manifest-only` explicitly requests a stored
  snapshot.
- Runtime SEO endpoints preserve configured origin pathname bases, normalize
  host authority, implement `GET`/bodyless `HEAD` parity, and enforce total URL,
  rendered-byte, and hard-deadline budgets. Explicit `HEAD` is registered before
  same-path `GET` so Fastify's automatic HEAD sibling does not collide.
- Model discovery produces a validated plan before mutation. Strict validation
  is the default; explicit lenient mode skips only invalid discovery inputs.
  Commit is atomic, app-owned registrations are reference-counted, and close
  never clears another application's models.
- Plugin setup, bootstrap providers, route execution, and request adapters expose
  abort signals backed by hard deadlines. Framework mutations are transactional,
  late continuations are revoked, and late rejections are observed.
- Session persistence completes before the response send barrier, shares one
  in-flight commit across explicit and automatic saves, and fails before a
  success response or cookie is sent. Expired memory entries are removed through
  bounded opportunistic cleanup.
- CommonJS root/testing/frontend/style/adapter entrypoints share runtime type and
  logger identity. ESM-only preload resolution is cached per project, resolution
  base, and target identity instead of by bare request alone.
- Machine documentation derives page stability from the version-channel truth
  source. CI verifies lint, changed-file format, package and rendered-doc
  contracts, and a representative Windows/Node 22 path/package lane before
  `CI ✅` succeeds.

## Breaking and behavioral changes

### Database access

- `app.db` is the raw MonSQLize instance and is the canonical entry point for
  collections, models, transactions, pools, events, and diagnostics.
- The duplicate `app.monsqlize` surface is removed.
- Model lookup no longer synthesizes prefixed aliases. Local models may
  deliberately replace the same shared model key; duplicate local keys,
  pre-existing registry collisions, and alias collisions fail before partial
  registration.

### Validation status codes

- Invalid path parameters declared through `validate.param` return HTTP `400`.
- Body, query, header, and cookie validation failures return HTTP `422`.
- Generated OpenAPI error responses accept the runtime's string or integer
  error codes, object or array details, and field-level `errors[]` entries.

### Route metadata projection

The build-time route index uses a finite static grammar and never executes
application code. It binds a named `defineRoutes` import from `vextjs` (including
an import alias) to a finite set of default-export forms: an inline synchronous
factory, or a same-file top-level route-definition binding exported as default. Re-exports,
imported factories, callback identifiers, property/namespace callees, async
factories, and missing default exports fail with source context; unused phantom
`defineRoutes` calls do not become routes.

Route options accept literals, same-file `const` bindings, TypeScript `as const`
/ `satisfies` wrappers, and canonical `schemaAdapter.compileField(<static
string>)` builders with an optional static `.description(...)`. Helper calls
around route options, opaque third-party schema objects, dynamic builder chains,
conditional registration, and nested registration fail with route context.
Comments, strings, template text, and regular expressions are excluded from
structural matching.

Dynamic paths or dynamic `validate` / response-schema expressions now stop the
build with file, method, and route context instead of silently omitting a route
or emitting an empty contract. Request contracts reuse the same canonical
schema projection as the frontend/client contract pipeline.

At runtime, `defineRoutes()` also enforces the synchronous factory contract.
Native async factories fail before execution, while custom thenables are
rejected transactionally without retaining partially registered routes or
removing the route helper methods. Minified CJS output may lower consecutive
statements, including non-registrar app configuration followed by routes, into a
top-level comma sequence; runtime accepts that compiler form while still
rejecting gated routes. The source scanner continues to require direct route
statements.
Direct access to non-registrar `VextApp` capabilities is not treated as a route;
naked app helper delegation and non-canonical registrar access still fail closed.

### Scaffold and type ownership

- New TypeScript starters run `vext build --typecheck` from their generated
  `build` script.
- TypeScript projects may receive the Vext-managed
  `src/types/generated/index.d.ts` shim. JavaScript create/dev/typegen flows do
  not create that public TypeScript source tree; tooling-only declarations
  remain under `.vext/types`.
- Type checking invokes only the project's installed `tsc`; there is no
  network-capable `npx tsc` fallback.

### Documentation, configuration, and scaffold corrections

- The public path-aware `VextConfigOverride` type represents later config-layer
  patches without weakening the strict `VextUserConfig` base contract. Atomic
  adapters, stores, clients, callbacks, arrays, and discriminated capabilities
  remain indivisible; the testing entrypoint uses the same override contract.
- An independent `test:types` project exercises positive and negative source
  contracts, while the packed-install consumer repeats the public root/testing
  declaration checks against the installed package. The source fixture is part
  of GitHub, Bash, PowerShell, and source preflight qualification immediately
  after the main typecheck.
- New TypeScript and JavaScript starters expose active `local` and `bootstrap`
  config files instead of `.example` files. The local override is empty and
  ignored by Git, while bootstrap starts with `providers: []`; neither enables
  debug logging, providers, external connections, or business side effects.
- Documentation now assigns service implementations, server-only types, shared
  DTOs, runtime constants, and stateless cross-module utilities to explicit
  scanner-safe directories. These support modules remain ordinary imports and
  are not projected as services or injected on `app`.
- Configuration examples distinguish a strict base config from later override
  layers, including the TypeScript rule that a base `database` object cannot rely
  on a later profile to satisfy its required `config` field.
- Deployment guidance no longer implies that VextJS parses `.env` files. External
  tooling may still populate `process.env`, and scaffold ignore rules continue to
  protect `.env*` and local overrides from accidental commits.
- Public package, README, bilingual homepage/introduction, site metadata, and
  generated machine-documentation inputs now use the bounded AI-first meaning;
  the stale hard-coded homepage version label was removed.

## Reliability fixes

- SEO defaults and route SEO now share deep normalization for alternates,
  Open Graph, Twitter, images, robots, and JSON-LD. Required nested fields and
  JSON-safe values fail early.
- Robots values reject control characters, request-host origin ambiguity fails
  configuration, and endpoint conflict checks recognize a bare `*` wildcard.
- SEO artifacts use exclusive commit semantics and roll back only files
  committed by the current writer, preserving a concurrent owner's target.
- Fastify keeps ownership of delayed streaming SSR responses until the stream
  sends instead of finalizing an empty body.
- Pull requests execute the coverage job required by the aggregate `ci-ok`
  gate.
- Changed-file formatting uses the tracked `.gitignore` as its deterministic
  ignore source and compares the complete PR/push delta, preventing local
  ignores or a clean merge checkout from weakening the CI gate.
- Deleted or renamed model files release their app-owned registry keys through
  the same atomic hot-reload source transaction used for updates.
- A failed asynchronous session commit discards the buffered success response
  on Native, Express, Fastify, Koa, and Hono before the adapter emits its normal
  error response; the rejected in-flight commit is observed immediately and
  still propagates through the send barrier.
- TypeScript service loading waits for temporary compiled-module cleanup before
  returning, preventing Windows teardown from racing a still-pending unlink.
- Final release preflight resolves external-consumer evidence from the current
  package major (`v2-external-validation.json` for `2.0.0`) rather than reusing
  the historical v1 evidence file.

## Migration checklist

1. Replace `app.monsqlize` access with `app.db`.
2. Use exact registered model keys and resolve any duplicate local/shared/alias
   registrations reported during startup.
3. Set `rateLimit.enabled: true` if the application relied on an implicit
   global limiter.
4. Update clients and tests that treated invalid path parameters as `422` to
   expect `400`; keep `422` for body/query/header/cookie failures.
5. Keep build-indexed route paths and schemas within the documented static
   grammar. Move request-dependent SEO to `res.render(..., { seo })`.
6. Ensure TypeScript projects install `typescript` locally; generated starter
   builds now fail when semantic type checking fails.

  source candidate. They do not create or imply a separately released `2.0.1`.
