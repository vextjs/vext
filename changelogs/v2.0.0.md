# vextjs v2.0.0 candidate

**Candidate snapshot**: 2026-08-24
**Type**: Unpublished major-version candidate

## Status

This file describes the source candidate currently identified as `2.0.0`. It
does not claim that an npm package, Git tag, GitHub Release, or stable channel
has been published. Final publication remains blocked until genuine 2.x
external-consumer evidence is available at
`release/v2-external-validation.json` and the release channel is explicitly
chosen.

## Highlights

- Framework-owned SEO metadata, canonical URLs, robots directives, sitemap
  entries, route-level overrides, and named deployment origins.
- Route-level `hydration: "none"` for server-rendered HTML that intentionally
  ships no Vext/React browser runtime, hydration payload, or route JS preload.
- A single raw MonSQLize surface at `app.db`, with exact registered model keys
  and explicit collision handling.
- Opt-in global rate limiting: it is installed only when
  `rateLimit.enabled === true`.
- Executable Hello World and MongoDB CRUD examples covering build, runtime,
  validation, and OpenAPI behavior.
- Explicit TypeScript starter ownership under `src/types/shared`,
  `src/types/frontend`, and Vext-managed `src/types/generated`.

## Breaking and behavioral changes

### Database access

- `app.db` is the raw MonSQLize instance and is the canonical entry point for
  collections, models, transactions, pools, events, and diagnostics.
- The duplicate `app.monsqlize` surface is removed.
- Model lookup no longer synthesizes prefixed aliases. Local models may
  deliberately replace the same shared model key; duplicate local keys,
  pre-existing registry collisions, and alias collisions fail before partial
  registration.

### Validation status codes

- Invalid path parameters declared through `validate.param` return HTTP `400`.
- Body, query, header, and cookie validation failures return HTTP `422`.
- Generated OpenAPI error responses accept the runtime's string or integer
  error codes, object or array details, and field-level `errors[]` entries.

### Route metadata projection

The build-time route index uses a finite static grammar and never executes
application code. It accepts literals, same-file `const` bindings, TypeScript
`as const` / `satisfies` wrappers, and a helper call whose first argument is a
statically projectable options object. Comments, strings, template text, and
regular expressions are excluded from structural matching. Route registration
must be a direct top-level statement in the `defineRoutes` callback;
conditional or nested registration fails with route context instead of
creating a phantom build contract.

Dynamic paths or dynamic `validate` / response-schema expressions now stop the
build with file, method, and route context instead of silently omitting a route
or emitting an empty contract. Request contracts reuse the same canonical
schema projection as the frontend/client contract pipeline.

### Scaffold and type ownership

- New TypeScript starters run `vext build --typecheck` from their generated
  `build` script.
- TypeScript projects may receive the Vext-managed
  `src/types/generated/index.d.ts` shim. JavaScript create/dev/typegen flows do
  not create that public TypeScript source tree; tooling-only declarations
  remain under `.vext/types`.
- Type checking invokes only the project's installed `tsc`; there is no
  network-capable `npx tsc` fallback.

## Reliability fixes

- SEO defaults and route SEO now share deep normalization for alternates,
  Open Graph, Twitter, images, robots, and JSON-LD. Required nested fields and
  JSON-safe values fail early.
- Robots values reject control characters, request-host origin ambiguity fails
  configuration, and endpoint conflict checks recognize a bare `*` wildcard.
- SEO artifacts use exclusive commit semantics and roll back only files
  committed by the current writer, preserving a concurrent owner's target.
- Fastify keeps ownership of delayed streaming SSR responses until the stream
  sends instead of finalizing an empty body.
- Pull requests execute the coverage job required by the aggregate `ci-ok`
  gate.
- TypeScript service loading waits for temporary compiled-module cleanup before
  returning, preventing Windows teardown from racing a still-pending unlink.
- Final release preflight resolves external-consumer evidence from the current
  package major (`v2-external-validation.json` for `2.0.0`) rather than reusing
  the historical v1 evidence file.

## Migration checklist

1. Replace `app.monsqlize` access with `app.db`.
2. Use exact registered model keys and resolve any duplicate local/shared/alias
   registrations reported during startup.
3. Set `rateLimit.enabled: true` if the application relied on an implicit
   global limiter.
4. Update clients and tests that treated invalid path parameters as `422` to
   expect `400`; keep `422` for body/query/header/cookie failures.
5. Keep build-indexed route paths and schemas within the documented static
   grammar. Move request-dependent SEO to `res.render(..., { seo })`.
6. Ensure TypeScript projects install `typescript` locally; generated starter
   builds now fail when semantic type checking fails.

## Release blockers and non-claims

- `release/v2-external-validation.json` must come from a real external
  consumer run for the exact candidate artifact; it is intentionally not
  generated by this repository repair.
- The stable-versus-RC/next channel decision is not encoded in this source
  repair.
- Local tests, documentation checks, or a dry run do not substitute for remote
  CI, registry identity, publish authorization, or post-release verification.
